# CMS «АлаДея»: архитектура и эксплуатация

Документ описывает административную панель, хранение данных и путь переноса на полноценный сервер.

## 1. Что было до CMS

Публичный сайт был статическим: 12 карточек товаров лежали прямо в `index.html`, данные корзины — в `localStorage`, заказ открывался в WhatsApp. GitHub Pages не даёт серверной авторизации, базы данных и защищённой загрузки файлов, поэтому CMS нельзя было сделать «поверх» Pages.

## 2. Выбранная архитектура

```
Браузер
  ├── публичная витрина  ── SSR из SQLite (index.html + серверная вставка карточек)
  └── /admin             ── серверные сессии, CSRF, роли администратора
                              │
                        Node.js + Express
                         ├── SQLite (node:sqlite) — реальная БД в data/aladea.sqlite
                         ├── sharp + multer — загрузка, проверка и сжатие фото
                         └── data/uploads — файловое хранилище вне исходников
```

Публичная часть по-прежнему использует тот же дизайн, CSS и JavaScript. Сервер подставляет актуальные категории, карточки и количество позиций в HTML перед отправкой. Если БД пустая, срабатывает сид с текущим каталогом.

### Почему сейчас SQLite

В окружении не было PostgreSQL/Docker и не было Supabase-проекта или ключей. Использовать фиктивные ключи и «псевдобазу» нельзя, поэтому рабочая версия сделана на встроенном SQLite:

- это настоящая транзакционная БД, а не mock;
- не требует внешнего сервиса и API-ключей;
- данные и загрузки лежат в `data/` и не попадают в Git;
- для одного небольшого сайта SQLite на VPS — нормальный вариант;
- SQL-схема и серверный слой изолированы, чтобы перейти на PostgreSQL без переписывания интерфейса. Заготовка схемы для PostgreSQL/Supabase лежит в `server/sql/schema.postgres.sql`.

### Почему не Supabase сразу

Для Supabase нужны project URL, anon key и service role key (последний — только на сервере), а также настроенные RLS/Storage. Без реального проекта нельзя проверить авторизацию, загрузку и публичную выдачу. Когда появятся доступы, можно перейти на Supabase/PostgreSQL, не меняя UX панели.

## 3. Данные

| Таблица | Назначение |
| --- | --- |
| `administrators` | email, scrypt-хеш пароля |
| `categories` | название, slug, порядок |
| `products` | название, slug, описание, цена, старая цена, вес, категория, главное фото, публикация, наличие, акция, порядок |
| `product_images` | дополнительные изображения товара |
| `admin_sessions` | хеш серверной сессии, CSRF-токен, срок действия, IP/UA |
| `login_attempts` | ограничение попыток входа |

Цена `NULL` означает «цена по запросу» — товар не добавляется в корзину. Скрытые товары (`published = 0`) не попадают ни в публичный HTML, ни в `/api/catalog`, но видны в админке.

## 4. Безопасность

- пароли — `scrypt` (`N=16384`, случайная соль);
- сессия — случайный 256-битный токен, в БД только SHA-256 хеш; cookie `HttpOnly`, `SameSite=Lax`, `Secure` в production;
- CSRF-токен для каждой административной формы и POST;
- проверка авторизации на сервере для всех `/admin`-маршрутов;
- ограничение попыток входа: 5 за 15 минут по IP/email;
- загрузки: только JPG/PNG/WebP, проверка через `sharp`, лимит 8 МБ, перекодирование в WebP с ограничением 1600 px;
- файлы вне исходников: `data/uploads`, имена генерируются случайно;
- заголовки: CSP, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, HSTS в production;
- админка закрыта `noindex`, `Cache-Control: no-store`, `/admin` в `robots.txt`;
- SQL — только параметризованные запросы;
- публичный API отдаёт только опубликованные товары.

### Что понадобится для Supabase

Если переходим на Supabase, нужны:

1. `SUPABASE_URL`;
2. `SUPABASE_ANON_KEY` — можно отдавать браузеру;
3. `SUPABASE_SERVICE_ROLE_KEY` — **только на сервере**, никогда в клиентском JS;
4. имя Storage bucket для фото;
5. email администратора (аккаунт создаётся в Supabase Auth).

Без этих данных текущая версия остаётся на SQLite. Секреты не выдумываются и не коммитятся.

## 6. План переноса на PostgreSQL/Supabase

1. Создать проект Supabase/Neon, применить SQL-схему (таблицы выше, `uuid`/`bigserial`, `timestamptz`).
2. Перенести `server/db.mjs` на `pg`/`postgres`-клиент, сохранив функции `all/get/run/transaction`.
3. Перенести фото из `data/uploads` в Supabase Storage или S3; в БД хранить публичные URL.
4. Включить RLS: анонимный SELECT только по `published = 1`; запись — только через сервер/authenticated admin.
5. Настроить Auth или оставить серверные сессии (рекомендуется серверный вариант, если админ один).
6. Подключить домен, HTTPS, бэкапы и мониторинг.
7. Прогнать E2E-сценарии на staging.

## 7. Запуск текущей версии

```bash
# из папки aladea
pnpm install
cp .env.example .env
npm run db:seed          # опционально; сервер также сидит пустую БД
npm run admin:create     # спросит email и пароль
npm start
```

Админка: `http://127.0.0.1:3000/admin` — не linked из публичной навигации.

Production:

```bash
NODE_ENV=production COOKIE_SECURE=1 TRUST_PROXY=1 DATA_DIR=/srv/aladea/data npm start
```

За обратным прокси с HTTPS. Хранить `data/` на persistent volume, делать ежедневный бэкап SQLite и `uploads`.

## 9. Проверено

E2E-сценарий проверяет:

- редирект неавторизованного пользователя;
- вход с CSRF и серверной сессией;
- создание товара с главным и дополнительным фото;
- отдачу изображения в WebP;
- редактирование цены и удаление дополнительного фото;
- скрытие товара из публичного API и HTML;
- отказ при отсутствии CSRF;
- создание категории, перенос товара и безопасное удаление категории;
- удаление товара и файлов;
- выход и инвалидацию сессии.
